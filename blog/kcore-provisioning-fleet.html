Manage a server fleet with kcore-provisioning

15 October 2026

← Back to blog

It is fine to install one kcore node from an evaluation ISO in a lab, but a rack of PowerEdge boxes is a different matter. You need a list of machines, a verified image, a boot target, and a way to power the BMC without walking the aisle with a KVM.

That is what kcore-provisioning is for. The provisioner sets up servers using IPMI and Redfish and netboots kcore via UEFI HTTP boot. The dashboard below is the operator view of that controller: images, machines, boot configurations, and power. The screenshots are from a lab install; the layout of the UI is what matters.

What the dashboard shows

The overview is one page for fleet health. It shows total and verified OS images, total machines, and how many are provisioned, provisioning, or failed. It refreshes every ten seconds from the provisioning controller API. Quick links go to Images, Machines, and Boot Configs. Recent activity lists the latest provisioning events when any exist.

You do not open a spreadsheet to find out which hosts are ready. You open Overview.

Feature list

  • Verified OS images — downloaded images with name, version, architecture, type, verification status, size, and created time. Filter by verified, pending, or failed.
  • Machine inventory — registered physical servers with name, MAC, IP, state, power state, manufacturer, model, and assigned boot target.
  • BMC / iDRAC detail — per machine: manufacturer, model, serial, CPU, cores, memory, BMC IP and firmware, NIC MACs, and storage devices from the BMC.
  • Power control — Power On, Power Off, and Reset from the machine page. The dashboard footer states this UI is power control for interactive actions; install progress still comes from the provisioner pipeline.
  • Drive health — ask the BMC about each drive and re-check without a separate hardware tool.
  • Boot configurations — which machine boots which image, with MAC, kernel parameters when set, and a config URL you can view or download.
  • Netboot path — UEFI HTTP boot of kcore after BMC configuration over IPMI or Redfish, not a USB stick per host.
  • API-backed — the page reads the provisioning controller API, so the same facts can feed automation instead of living only in a console.

Why a fleet is easier this way

Manual installation does not scale past a few nodes. Someone has to image each disk, set the boot order, and track which MAC got which build. With kcore-provisioning the loop is shorter:

  • Register or discover the machine once. The inventory stores MAC, BMC address, model, and NICs.
  • Keep a small set of verified images. Operators pick a known-good version instead of copying ISOs by hand.
  • Attach a boot configuration to the machine. The target image is explicit and downloadable.
  • Power the host from the same page when you need to reboot into the netboot path.
  • Watch Overview for provisioned versus failed while the controller does the work.

That is the same idea as launching a cloud instance — desired image, inventory, and power — on hardware you already own.

A machine page in practice

Opening one host shows why this is faster than a BMC-only workflow. Power controls sit next to drive health. System information, CPU and memory, BMC firmware, NICs, and storage are on one screen. Provisioning status links the boot target and lets you download the config. You are not bouncing between iDRAC, a PXE server UI, and a wiki page for the kernel line.

Where this sits in kcore

Day to day, after nodes are installed, VM and cluster work still goes through kctl, YAML, and the Terraform provider. The provisioner is the entry point for getting bare metal into that fleet. Community Edition install from the evaluation ISO remains the path for a single host or a small lab. The provisioner is the path when the unit of work is a rack, not a laptop.

For IPMI, Redfish, and UEFI HTTP boot, see features. For node join and approval after install, see the add-node and installation guides.

Conclusion

Fleet management on bare metal fails when inventory, images, boot targets, and power live in four tools. kcore-provisioning puts those facts in one controller and one dashboard. Verified images, discovered machines, boot configs, and BMC power are enough to stop treating every new server as a special project.
