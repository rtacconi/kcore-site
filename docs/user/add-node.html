Add a node to the cluster

← User documentation

This page describes how to install kcore on a new bare-metal machine, join it to your controllers, and move it from pending to approved so it can schedule VMs.

Prerequisites

  • A running controller (or HA pair) reachable from your operator workstation.
  • kctl configured with your cluster TLS context (~/.kcore/<context>/).
  • The new machine booted from the kcore ISO or live environment, reachable at <NEW_NODE_IP>:9091.

Discover hardware

kctl --node <NEW_NODE_IP>:9091 node disks
kctl --node <NEW_NODE_IP>:9091 node nics

Install to disk

kctl signs a node certificate with your cluster CA and sends an install request to the node agent. The OS disk is prepared with LUKS (TPM-sealed when TPM2 is available). Controllers and datacenter ID are written into node configuration.

kctl --node <NEW_NODE_IP>:9091 node install \
  --os-disk /dev/sda \
  --join-controller 192.168.40.105:9090 \
  --join-controller 192.168.40.106:9090 \
  --dc-id DC1

Optional flags include --data-disk (repeatable), --storage-backend, LVM/ZFS names, and --disable-vxlan. After install the node reboots into the installed system.

Registration and approval

After boot, the node agent registers with the controller and appears as pending. Pending nodes cannot run workloads until you approve them.

kctl get nodes
kctl node approve <NODE_ID>

Use kctl node reject <NODE_ID> if the registration is unexpected. Rejected nodes stay rejected until you explicitly approve them later.

Approval is the human gate on top of mTLS: even with a valid client certificate, a node does not participate in scheduling until approved.

Certificates

Node certificates are renewed automatically when within 30 days of expiry. Operators can rotate the sub-CA with kctl rotate sub-ca. Use kctl get nodes to inspect certificate expiry.
