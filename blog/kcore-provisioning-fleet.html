    • It is acceptable to install one kcore node from an evaluation ISO in a laboratory environment, but setting up a rack of PowerEdge boxes is a different matter. You need a list of the machines, a verified image, a boot target, and a method of powering the BMC without having to walk down the aisle with a KVM.

    That's the purpose of kcore-provisioning. The provisioner sets up the servers using IPMI and Redfish and netboots kcore via UEFI HTTP boot. The dashboard shown below represents the operator's view of that controller: it includes the images, the machines, the boot configurations, and the power settings. The screenshots are from a lab installation; it is the layout of the UI that is important.

    What the dashboard shows

    The overview occupies one page and provides information about fleet health, including the total number and the number of verified OS images, the total number of machines, and how many are provisioned, in the process of being provisioned, or have failed. It automatically refreshes every ten seconds by retrieving data from the provisioning controller API. Quick links allow you to go directly to Images, Machines, and Boot Configs, and the Recent activity section lists the most recent provisioning events whenever there are any.

    You don't open a spreadsheet in order to find out which hosts are ready; instead, you open Overview.

    Feature list

    • Verified OS images: these are images that have been downloaded and include details such as name, version, architecture, type, verification status, size, and the time at which they were created. The images can be filtered according to whether their verification status is verified, pending, or failed.
    • Machine inventory: the physical servers that are registered, including details such as their name, MAC address, IP address, status, power state, manufacturer, model, and the boot target that has been assigned to them.
    • BMC / iDRAC detail: for each machine, the manufacturer, model, serial number, CPU, number of cores, memory, BMC IP address and firmware, the NIC MAC addresses, and the storage devices as reported by the BMC.
    • Power control: Power On, Power Off, and Reset from the machine page. The footer on the dashboard indicates that this UI serves as power control for interactive actions; install progress still comes from the provisioner pipeline.
    • Drive health: ask the BMC about each drive and then verify it again without using a separate hardware tool.
    • Boot configurations: which machine boots which image, including the MAC address, the kernel parameters when set, and a config URL that can be viewed or downloaded.
    • Netboot path: UEFI HTTP boot of kcore following BMC configuration via IPMI or Redfish, not a USB stick for each host.
    • API-backed: the page accesses the provisioning controller's API, allowing the same information to be used by automation rather than being available only through the console.

    Why a fleet is easier this way

    Manual installation cannot be extended beyond a small number of nodes since someone has to image each disk, set the boot order, and keep track of which MAC address was assigned to which build. With kcore-provisioning the process becomes shorter:

    • Register or discover the machine once. The inventory stores the MAC address, the BMC address, the model, and the NICs.
    • Maintain a small number of verified images. Operators select a known-good version rather than copying the ISOs by hand.
    • Add a boot configuration to the machine. The target image is specific and can be downloaded.
    • Power the host from the same page when you need to reboot into the netboot path.
    • Watch Overview for provisioned versus failed entries while the controller carries out its task.

    It is based on the same principle as launching a cloud instance—specifying the desired image, keeping track of the inventory, and providing power—on the physical hardware that you already own.

    A machine page in practice

    Opening one host shows why this is faster than a BMC-only workflow. The power controls are located beside the drive health information, and on the same screen you find system information, the CPU and memory, the BMC firmware, the NICs, and the storage. The provisioning status links the boot target and allows you to download the configuration. You don't have to switch from iDRAC to the PXE server's UI and then to a wiki page to get the kernel line.

    Where this sits in kcore

    From day to day, once the nodes have been installed, the management of virtual machines and clusters is still carried out using kctl, YAML and the Terraform provider. The provisioner serves as the entry point for getting bare metal into that fleet. When setting up a single host or a small lab, Community Edition installation from the evaluation ISO is the method to use. The provisioner is the method to use when the unit of work is a rack and not a laptop.

    Regarding product framing for IPMI, Redfish, and UEFI HTTP boot, refer to the features page. As for node join and approval following installation, see the add-node and installation guides.

    Conclusion

    Fleet management fails if the inventory, the images, the boot targets, and the power are spread across four different tools. kcore-provisioning brings all of these elements into a single controller and a single dashboard, so that you no longer have to treat each new server as if it were a special project.
