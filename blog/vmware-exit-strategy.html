VMware exit strategy: choosing the right platform

15 October 2026

← Back to blog

Comparing kcore with Proxmox, Nutanix, OpenShift Virtualization, OpenStack, and OpenNebula for teams that need a real path off VMware.

The VMware market changed. Many organizations are looking again at alternatives. For years VMware was the default for enterprise virtualization. The stack was mature, the tooling was familiar, and operators knew the model. Licensing, commercial flexibility, and strategic control pushed a different question: not only “what replaces VMware?”, but “what operating model do we want next?”

That distinction matters.

A VMware exit is not a hypervisor swap. It is a decision about cost structure, skills, automation, storage and network integration, migration risk, and how much vendor lock-in you will accept on the next platform. The right answer depends on whether you need basic virtualization, a Kubernetes-first stack, a full private-cloud control plane, or a VM-first platform that still speaks APIs and Terraform.

The real criteria for a VMware replacement

Headline feature lists are a weak filter. A replacement has to cover the work you already do: create and place VMs, attach storage and networks, keep guests available, back them up, and support the hardware your applications need, including GPUs when that is required.

That is only the first layer.

Teams also want cloud-style operations: an API, declarative config, reviewable changes, and a path that does not force every change through a proprietary console. Terraform and YAML matter here because they turn the estate into text you can diff and audit.

Kubernetes support matters, but in context. Some estates are already Kubernetes-first. Many still run a large VM estate and need a platform that can host Kubernetes later without forcing every workload through a redesign on day one.

Migration tooling is part of the platform choice. Inventory, disk conversion, and cutover are different jobs. A credible exit plan names who does each job and what remains a project.

The platform landscape

Several platforms compete for attention. Each has a different center of gravity.

  • VMware Cloud Foundation is the lowest-change path if you stay inside VMware. You keep the operating model and the ecosystem. You also keep the commercial exposure that started the exit discussion.
  • Nutanix is a strong HCI-led option when an appliance-style stack is the priority. Integration can be attractive. Cost and platform dependency are the usual trade-offs for teams that left VMware because pricing and lock-in became hard to accept.
  • Proxmox is appealing for smaller environments, labs, and teams that want straightforward KVM virtualization at a lower cost. Simplicity is a strength. It is a weaker fit when you want a first-class API, Terraform as the default workflow, and a productized path from inventory to guest definitions on another hypervisor.
  • Red Hat OpenStack fits large IaaS estates with dedicated platform engineering. The operational burden is real. Many teams cannot justify that lifecycle cost unless they already run OpenStack skills in-house.
  • Red Hat OpenShift Virtualization is a Kubernetes-first option. It fits when Kubernetes is already the main operating model and VMs are secondary. It is not always the most natural fit for a VM-first VMware replacement.
  • OpenNebula targets enterprises that want VM operations plus a broader private-cloud and multi-tenant model, including elastic Kubernetes in that same story. If your requirement is a full open private cloud with that shape, evaluate it on those terms.

Where kcore fits

kcore is a VM-first hypervisor product for teams that want to leave VMware pricing without moving into another closed appliance stack. Guests are managed with kctl, YAML manifests, and the Terraform provider kcorehypervisor/kcore. The provider talks to the kcore API over gRPC. That is a normal IaC workflow, not a shell wrapper.

Pricing is per physical CPU socket per year, not per core. The Community Edition ISO and kctl are on GitHub Releases under Apache-2.0. Paid tiers fund the signed distribution, the enterprise update channel, and commercial support. See pricing.

Host updates are designed so a failed update boots the previous generation. Windows Server and Windows desktop guests run. Live migration of a VM needs shared Ceph storage; control-plane replication across datacenters is not vSphere HA. One physical GPU can be assigned to one VM; NVIDIA vGPU is not available. Those limits are documented on the features page so you can plan honestly.

Kubernetes is available as clusters on nodes that are already in the kcore cluster. That supports a gradual path: keep VM-first operations, then add Kubernetes where it helps. It is not a claim that every Kubernetes-first platform feature ships on day one.

For migration, kcore-migrate inventories vCenter or Proxmox and writes Terraform for kcore, plus a gap report. convert turns an exported disk into qcow2 or raw with virt-v2v or qemu-img. It does not pull disk bytes straight from vCenter. Cutover remains a project. The operator steps are in the import guide. A deeper split of inventory tools, disk movers, and Terraform generators is in Three kinds of VMware migration tool.

Match the platform to the operating model

The useful comparison is not “who has the longest feature list?” It is “what operating model do we want to run for the next five years?”

  • Small environments and technical teams often land on Proxmox.
  • Appliance-style HCI often lands on Nutanix.
  • Large engineering-led IaaS often lands on OpenStack.
  • Kubernetes-first organizations often land on OpenShift Virtualization.
  • Private-cloud and multi-tenant IaaS requirements often land on OpenNebula or similar stacks.
  • VM-first estates that want per-socket commercial terms, reviewable Terraform and YAML, a free evaluation ISO, and a migration path that writes destination HCL often land on kcore.

If you need NetApp, Veeam, or another vendor certification as a hard gate, check that vendor’s support matrix for the platform you pick. Do not assume a blog post replaces that check.

Conclusion

Leaving VMware is a strategic infrastructure decision, not only a cost line. The wrong replacement recreates lock-in, adds operational weight you cannot staff, or forces an operating model that does not match the workloads you still run.

The best alternative is the one that fits your architecture, skills, commercial priorities, and cloud timeline. For teams that want a practical VM-first exit with API and Terraform as normal tools, kcore is built for that path.
