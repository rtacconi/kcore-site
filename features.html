What kcore does

VMs, containers, and Kubernetes on an immutable host. HA, live migration, Ceph, and updates that roll back. Backup and bare-metal provisioning as add-on products.

Read this first

  • An update goes to one canary node first. A node that fails its health check boots the previous generation.
  • A host that dies is fenced and its VMs restart on the survivors. Live migration and failover need the disk on shared Ceph. A ZFS VM with a current replica restarts on its replica node.
  • Windows Server and Windows desktop guests run next to Linux.
  • A GPU goes to one VM, or an NVIDIA card is sliced into vGPUs. Intel and AMD SR-IOV slices are in the API but not yet run on lab hardware. VFIO devices do not live-migrate.
  • Dashboard sign-in is password and TOTP. There is no SSO yet.
  • kcore-migrate inventories vCenter or Proxmox and converts exported disks to qcow2 or raw. It does not read disks straight from vCenter. Cutover is a project. See the import guide.
  • The hypervisor is priced per CPU socket per year. The community ISO is free on GitHub Releases. Vault and Provisioning are separate paid products.

Updates try one node first and roll back

kctl update version set v0.7.0 resolves a release tag and starts a rollout. The canary soaks while the controller compares it with the other nodes. The rest follow one at a time.

  • ✓
    Immutable base
    The host OS is read-only. A change is a new generation, not an edit.
  • ✓
    Canary and soak
    Version, heartbeats, guest starts, agent errors, and Ceph OSD latency are compared. A bad canary rolls back and the rollout stops.
  • ✓
    Revert without the controller
    A guard timer and a one-shot boot entry put the previous generation back if the node does not report healthy. A kernel that hangs falls back too.

For platform teams

One controller API behind kctl, the dashboard, the Terraform provider, and an MCP server. The same roles and the same audit log apply to all of them.

Infrastructure as Code

VMs are resources in Terraform. You write HCL, run terraform apply, and the provider talks to the kcore API over gRPC. Standard workflow, no special tooling.

  • 📝
    Real Terraform Provider
    Written in Go using the Terraform Plugin SDK. Not a shell wrapper.
  • 🔄
    Git-friendly
    HCL and YAML are text files. Diff them, review them, track changes over time.
  • 📊
    Desired State
    The controller stores desired state. Node agents reconcile. Standard controller pattern. 
# Provider kcorehypervisor/kcore 0.7.0
resource "kcore_vm" "web" {
  name               = "web"
  cpu                = 2
  memory_bytes       = 4294967296
  storage_backend    = "filesystem"
  storage_size_bytes = 53687091200
  image_url          = "https://example.com/debian.qcow2"
  image_sha256       = "<sha256>"

  nic {
    network = "production"
  }
}

resource "kcore_vm" "db" {
  name               = "db"
  cpu                = 4
  memory_bytes       = 8589934592
  storage_backend    = "lvm"
  storage_size_bytes = 214748364800
  image_url          = "https://example.com/debian.qcow2"
  image_sha256       = "<sha256>"

  nic {
    network = "production"
  }
}

MCP and an AI agent

kcore MCP works in Cursor, VS Code, Claude Desktop, and any client that speaks the Model Context Protocol. kctl agent is a chat page built into the binary. Both use the same tools and the same rule: ask, plan, then wait for your approval.

  • 🤖
    Questions first
    The agent asks for image URLs, checksums, networks, and keys. It does not guess them.
  • 💡
    A plan you can read
    Create, update, or refused because a field is immutable. Nothing changes until you approve.
  • 📈
    Your role, not the model’s
    The agent runs with your certificate or a read-only or vm-admin operator of its own. The controller enforces it.

Complete features

What ships in 0.7.0. Work that is still planned stays on the roadmap.

Virtual machines

  • Create, update, start, stop, and delete. YAML and Terraform.
  • Cloud-init, SSH keys, labels, and a wait for boot or SSH.
  • Windows Server and Windows desktop guests.
  • Serial console in the browser and from kctl console.
  • A GPU passed through to one VM, by name.
  • NVIDIA vGPU slices, which need an AI Enterprise vGPU manager package on the host. Intel and AMD SR-IOV slices use the same manifest and are not yet run on lab hardware.
  • NAT, bridge, and VXLAN networks, extra NICs, IPv6, and VLANs.
  • Security groups, DNAT, and an east-west filter on a bridge.
  • Live and cold migration on Ceph, LVM, and ZFS. A filesystem disk stays put.
  • HA: a dead host is fenced and its VMs restart by priority, with anti-affinity and admission control. A ZFS VM restarts from its replica.

Containers and ingress

  • OCI containers on containerd, beside VMs, on one workload API.
  • Ingress on Caddy with Coraza, automatic certificates, and a keepalived VIP.
  • Routes to a VM, an external address, or a Kubernetes Service.
  • WAF detect and block, rate limits, and IP allow and deny lists.

Storage

  • Filesystem, LVM, ZFS, and Ceph RBD volumes, including resize.
  • Snapshots, schedules, clone, restore, and flatten on Ceph, ZFS, and LVM.
  • New Ceph clusters encrypt OSD disks. An RBD volume can be LUKS-encrypted.
  • Ceph RBD volumes for VM disks, replicated across nodes.
  • Declarative disk layouts from the installer through day-2.
  • Changed-block export and import for a backup tool.
  • kcore Vault (paid): retain-until backups, a ZFS repository, and S3 Object Lock.

Cluster and host services

  • mTLS, RBAC, an audit log, certificate rotation, CRL, and OCSP.
  • Dashboard with password and TOTP sign-in, API tokens, a serial console, release rollouts, and HA events.
  • Multi-controller replication, including across datacenters.
  • Scheduler: most free memory, required labels, anti-affinity, overcommit.
  • ISO install, kcore-infect, approve, cordon, drain, and delete.
  • Update by release tag with a canary soak. A failed boot uses the previous generation.
  • kcore Provisioning (paid): IPMI and Redfish, UEFI HTTP boot, BIOS and RAID profiles, disk checks, PowerDNS, and Kea.
  • Appliance console on the node.
  • node_exporter and VictoriaMetrics.
  • Webhooks, an MCP server, kctl agent, and the Terraform provider.
  • PostgreSQL on the node, one database per node.
  • Kubernetes on kcoreOS with Cilium.
  • Slurm on kcoreOS. Compute nodes are left to slurmd.
  • ClickHouse on kcoreOS, with Keeper. A rolling change leaves a replica of each shard up.
  • kcore-migrate inventories vCenter or Proxmox and converts exported disks.
