Why kcore Is Written in Rust

25 March 2026

← Back to blog

kcore is a hypervisor control plane. It manages VM lifecycles, writes system-level NixOS configurations, talks to hardware through Unix sockets, and handles certificates for mTLS. This is systems programming. The language you pick for it matters a lot.

I wrote kcore in Rust, and I'd make the same choice again. Here's why.

No null, no surprises

Go has nil. Any pointer, interface, slice, map, channel, or function value can be nil, and if you forget to check, you get a runtime panic. In a long-running system service that manages VMs, a nil pointer dereference at 3 AM is not a minor inconvenience — it's an outage.

Rust doesn't have null. Instead, it has Option<T>: a value is either Some(T) or None, and the compiler forces you to handle both cases before you can use the inner value. You can't accidentally dereference something that isn't there. The same pattern applies to errors with Result<T, E> — every fallible operation returns an explicit success or failure, and the compiler won't let you ignore it.

In practice, this means entire classes of bugs that would show up as runtime panics in Go simply don't compile in Rust. For a control plane that other services depend on, that's a meaningful reliability advantage.

Type safety that actually catches things

Go's type system is deliberately simple. That simplicity is a feature for some projects, but for systems code it means the compiler lets through mistakes that a stronger type system would catch at build time.

Rust's type system is expressive enough to encode real invariants. Enums with associated data mean you can model VM states, RPC responses, and configuration variants as closed types — if you add a new variant, every match arm in the codebase has to handle it or the build fails. Traits let you define shared behavior without inheritance. Lifetimes ensure references are always valid. Generics are monomorphized, so there's no runtime type erasure and no hidden allocations.

The result is code where the compiler is actively helping you find mistakes during development, not after deployment.

Performance without compromise

Rust compiles to native code with no garbage collector. For kcore, this means predictable latency on gRPC calls, low memory overhead per node agent, and fast NixOS config generation even when managing many VMs on a single host.

Go is fast enough for many things, but GC pauses are real, and they're harder to reason about in latency-sensitive paths. In a system where the controller pushes config to nodes and nodes apply it in real time, you want deterministic performance. Rust gives you that by default.

Systems programming is where Rust shines

kcore interacts directly with the operating system: writing files to /etc/nixos, spawning nixos-rebuild as a subprocess, reading VM status from Cloud Hypervisor API sockets under /run/kcore, managing TLS certificates with strict file permissions. This is textbook systems programming.

Rust's ownership model means there are no data races when the node agent handles concurrent gRPC requests while a background rebuild is running. There are no use-after-free bugs when passing file descriptors between async tasks. The borrow checker is annoying sometimes, but it catches real concurrency bugs that would be subtle and dangerous in any other language.

The NixOS ecosystem speaks Rust

kcore runs on NixOS and uses Nix for its entire build and deployment pipeline. The NixOS community has increasingly adopted Rust for systems tooling. Projects like nix-ld, disko, and nil (the Nix LSP) are written in Rust. The Tvix project — a Rust reimplementation of the Nix evaluator — is one of the most significant efforts in the ecosystem.

Building kcore in Rust means it fits naturally into this ecosystem. Nix's Crane library makes Rust builds reproducible out of the box. Contributors from the NixOS community are already comfortable with Rust tooling. There's no impedance mismatch between the project's language and its deployment platform.

Correctness as a design value

A hypervisor control plane is responsible for other people's workloads. When it generates a NixOS configuration and pushes it to a node, that config gets applied as root. When it writes TLS certificates, the permissions have to be right. When it reports VM state, the data has to be accurate.

Rust's guarantees — no null, no data races, exhaustive pattern matching, explicit error handling — aren't academic niceties. They're practical safeguards for code that runs with high privilege and manages real infrastructure. In kcore's codebase, the Nix config generator escapes all user-controlled strings to prevent injection. The auth layer validates certificate Common Names with exhaustive matching. The disk path validator rejects traversal attempts at the type level. These patterns are natural in Rust because the language pushes you toward them.

It's more enjoyable to write

This is subjective, but it matters. Rust code is dense and expressive. Pattern matching, iterator chains, and the trait system let you write code that reads close to what it means. cargo clippy acts as a second reviewer. cargo test runs fast because there's no VM startup. The toolchain is cohesive in a way that Go's isn't — formatting, linting, testing, building, and auditing are all part of the same cargo workflow.

When you're building something from scratch and you're going to live in the codebase for years, the day-to-day experience of writing and reading the code matters. Rust makes that experience good.

The tradeoffs

Rust has a steeper learning curve than Go. Compile times are longer. The ecosystem for some areas (like ORMs or web frameworks) is less mature. These are real costs.

But for a systems project like kcore — where correctness, performance, and reliability are non-negotiable — Rust's tradeoffs land in the right place. The compiler catches bugs before they reach production. The runtime doesn't surprise you with GC pauses. The type system encodes your invariants so they can't be silently violated.

For infrastructure software that manages VMs on bare metal, that's exactly what you want.
