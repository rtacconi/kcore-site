Add nodes to the cluster

A single-node kcore deployment is useful for evaluation, but production workloads benefit from multiple nodes for scheduling headroom, high-availability controllers, and cross-datacenter replication. This page walks through expanding your cluster from one node to many.

Add a second node (agent only)

Boot the new machine from the kcore ISO. Once the live environment is up you can inspect its hardware and install:

kctl --node <NEW_NODE_IP>:9091 node disks
kctl --node <NEW_NODE_IP>:9091 node nics

Install the OS to disk and join the existing controller. This node runs the node agent only—no controller process:

kctl --node <NEW_NODE_IP>:9091 node install \
  --os-disk /dev/sda \
  --join-controller 192.168.40.105:9090 \
  --dc-id DC1

After reboot the node registers with the controller in pending state. Approve it to start scheduling workloads (see Registration and approval below).

Add a third node with a second controller

For HA you want at least two controllers. Add the --run-controller flag so the new node starts its own controller process alongside the agent:

kctl --node <NEW_NODE_IP>:9091 node install \
  --os-disk /dev/sda \
  --join-controller 192.168.40.105:9090 \
  --run-controller \
  --dc-id DC1

You now have two controllers sharing state. Update your kctl invocations to target both so the CLI can fail over transparently:

kctl -s 192.168.40.105:9090 -s 192.168.40.106:9090 get nodes

Cross-DC: add a node in DC2

Multi-datacenter deployments tag each node with a datacenter identifier. Install the node with --dc-id DC2 and --run-controller so it brings up a controller in the second site:

kctl --node <NEW_NODE_IP>:9091 node install \
  --os-disk /dev/sda \
  --join-controller 192.168.40.105:9090 \
  --run-controller \
  --dc-id DC2

Resources created on this node are tagged with DC2. Controllers across datacenters replicate state via conflict-free replicated data types (CRDTs), so each site maintains an eventually-consistent view of the cluster.

Registration and approval

After install and reboot, every node registers with the controller and enters pending state. Pending nodes cannot run workloads until explicitly approved:

kctl get nodes
kctl node approve <NODE_ID>

If a registration is unexpected or suspicious, reject it:

kctl node reject <NODE_ID>

Rejected nodes stay rejected until you explicitly approve them later.

Approval is the human gate on top of mTLS: even with a valid client certificate, a node does not participate in scheduling until approved.

Certificates

Node certificates are renewed automatically when within 30 days of expiry. Operators can rotate the sub-CA at any time:

kctl rotate sub-ca

Inspect certificate expiry for all nodes:

kctl get nodes

FlagDescription

--lvm-vg-name <name>LVM volume group name (only with --storage-backend lvm).
--zfs-pool-name <name>ZFS pool name (only with --storage-backend zfs).
