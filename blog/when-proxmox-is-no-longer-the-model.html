When Proxmox is no longer the operating model

5 August 2026

← Back to blog

Proxmox is a good hypervisor. The usual reason to leave is a bad one, and the usual reason to stay is a bad one too. Leaving because a slide called the UI legacy is a bad reason. Staying because the cluster already works, and therefore the operating model must be fine, is the other one. The operating model is what fails first.

Proxmox VE is Debian, KVM, LXC, and a web UI on port 8006. The API is real. pvesh is real. Community Terraform providers exist. If your operators live in that UI, your backups are Proxmox Backup Server, and nobody is asking for a diff when a VM changes, stay. A migration whose aim is to look modern costs a quarter you do not get back.

The fork is what a change means

The fork is not whether an API exists. Both sides have one. The fork is what a change is allowed to mean.

On Proxmox the cluster is the source of truth. The UI and the API change it. A script can make the same change. After the call, the thing you can review is the cluster. You can dump the config. You can keep a ticket. You do not, by default, have a file that was reviewed before the machine changed.

On kcore the host is a NixOS generation pinned to a flake revision. A failed host update boots the previous generation. That property belongs to the host. It is not a guest snapshot, and it is not a backup of the VM disk. Guests come back because the host came back. Their data is still the disk, plus whatever backup you actually run.

Guest desired state is text. kctl and YAML cover the product. Provider kcorehypervisor/kcore 0.5.0 is a Go provider on the Terraform Plugin SDK. It is not a shell wrapper. It creates VMs, volumes, clusters, and nodes. It does not inventory Proxmox. It has no migrate or drain resource, no Kubernetes resource, no PostgreSQL resource, and no GPU attribute. Those stay on kctl or YAML. kcore_vm storage_backend is filesystem, lvm, or zfs. Ceph for the VM is a kctl flag. A Ceph data disk is a kcore_volume with storage class ceph.

If you need the file more than the UI, keep reading. If you need the UI, you already have it. You installed Proxmox.

What you give up

The losses are specific. If they match the estate, stop on this page.

Proxmox Backup Server is a product. kcore does not have one. kctl backup writes a copy of the controller database. kctl restore controller replaces that database. Guest backup stays with your current tool. If PBS is why the estate is calm, do not trade it for a generation boot.

LXC is a Proxmox workload. kcore-migrate lists those containers in gaps.md. It does not turn them into kcore VMs. kcore containers are OCI images through nerdctl or docker. The docs call that early phase: a lab workflow, not a platform. If the estate is LXC, the gap report is the decision, and the decision is to stay.

Live migration on Proxmox covers the storage types Proxmox supports. On kcore, live migration needs shared Ceph RBD. Both nodes map the same image, and memory moves over TCP. Local filesystem, LVM, and ZFS disks do not move. A cold drain stops the guest and starts it somewhere else. A node that misses heartbeats for 90 seconds is marked not-ready. The controller then cold-moves each Ceph VM onto another member of the same cluster. It does not contact the failed node. Filesystem, LVM, and ZFS VMs stay where they are. That is not Proxmox HA. Control-plane replication across datacenters is not vSphere HA either.

One physical GPU per VM. There is no NVIDIA vGPU. A GPU guest can move cold onto a free card of the same family.

Windows Server and desktop guests run. That is not a Microsoft certification.

Three jobs, not a button

Inventory reads the Proxmox API. The password comes from PROXMOX_PASSWORD, not from a command-line flag. A host with no port is read on 8006. The reader lists QEMU virtual machines and LXC containers. Disks stay on the node. It writes guests.tf and gaps.md. guests.tf has one kcore_vm per guest: name, CPU, memory, the first disk size, and NICs. image_path is empty. storage_backend is filesystem until you change it. gaps.md holds the extra disks, the LXC containers, and the VLAN tags. Read gaps.md before guests.tf. If the gaps are the estate, stop. The commands are in the import guide.

Convert does not fetch the disk. You export it. A Proxmox qcow2, raw, or img file goes through qemu-img, which only changes the container format. An OVA or VMDK goes through virt-v2v. Then set image_path and image_format to qcow2 or raw. kctl accepts those two.

Cutover is a window you plan. Pick the slot, the address change, the test that says the guest is up, and a backout that does not need the new platform to be healthy. Live migration inside kcore does not lift a guest off Proxmox. The guest is created from the converted disk.

One node, then a decision

Run that on one node before you name a programme.

If gaps.md is longer than the announcement you were about to make, believe the file.

Export one disk. Convert it. Time the copy. That number, times the estate, is the length of the project.

Apply one guest with Terraform or YAML. If the team will not review the diff, you have rebuilt the same operating model with extra steps.

Fail a host update in a lab. The pass condition is that the previous generation boots, and that generation has to be one you are willing to run.

Then compare the money without comparing screenshots. Community Edition is Apache-2.0. The evaluation ISO and kctl are on GitHub Releases, with no subscription. Production support is per physical CPU socket per year, not per core. Enterprise has an 8-socket minimum. Proxmox subscriptions are per socket too. Put both yearly figures on one line. The operating model is the rest of the decision.

If PBS, LXC, or live migration without shared Ceph is load-bearing, stay. If what you needed was a reviewed file and a host that boots the last good generation, try the evaluation ISO on that one converted guest before you touch the cluster.
