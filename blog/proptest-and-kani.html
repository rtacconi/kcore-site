Why we use proptest and Kani in kcore

17 April 2026

← Back to blog

Unit tests catch the cases you thought of. The bugs that hurt in production are the ones you didn't. In kcore we run two extra layers on top of normal tests to close that gap on the code paths where a single missed case can corrupt a controller database, generate an unsafe Nix expression, or accept a path that escapes its root directory: proptest for property-based (generative) testing, and Kani for bounded model checking. Both are wired into CI and run on every pull request.

What Rust already gives us

kcore is written in safe Rust with no unsafe blocks. The compiler already eliminates whole classes of bugs: data races, use-after-free, null dereferences, buffer overflows. Every cargo build is, in effect, a small proof run. proptest and Kani are about the bugs Rust does not catch: logic errors, missed escape sequences, invalid state transitions, and inputs the author never imagined.

proptest: property-based testing

proptest generates random inputs guided by a strategy (any string, any integer, any struct of these) and checks that a property holds across hundreds of cases. When it finds a counterexample, it shrinks the input to the smallest failing case and prints it so you can write a unit test directly from the failure.

We use it in two places where the cost of being wrong is high:

  • Nix string generation in crates/controller/src/nixgen.rs. The output of these functions runs as root during nixos-rebuild switch. A missed escape on ", \, or ${ is not a typo, it is a privilege escalation. Properties we check: escape never produces an unescaped ${, sanitised attribute keys only contain [a-zA-Z0-9_-], generated configs always have balanced braces.
  • Database CRUD in crates/controller/src/db.rs. The controller's SQLite is the source of truth for the whole system. We run ~256 randomised cases per property against an in-memory database and assert round-trip equality, upsert idempotence, foreign-key integrity (a VM cannot reference a node that does not exist), delete consistency across every read path, and heartbeat idempotence modulo timestamp.

proptest is probabilistic. It cannot prove the absence of bugs. But it consistently finds the inputs a human would not have tried: empty strings, embedded NULs, very long names, characters in surrogate ranges, the exact byte that triggers an off-by-one. It is cheap to add and runs in milliseconds per property.

Kani: bounded model checking

Kani is Amazon's model checker for Rust. A Kani harness looks like a test, but instead of running one concrete input it explores every possible input within declared bounds and proves the assertions hold for all of them. Where proptest says "we tried many cases and none failed", Kani says "no input within these bounds can make this assertion fail".

We use Kani on small, pure functions where exhaustive proof is feasible:

  • nix_escape and sanitize_nix_attr_key in crates/controller/src/nixgen.rs — proven not to panic and proven to produce safely escaped output for all ASCII inputs up to the current bound.
  • path_segments_include_dot_dot and assert_safe_path in crates/controller/src/path_safety.rs and crates/kctl/src/path_safety.rs — proven total (no panic on any bounded input), and proven sound: any accepted path is non-empty, NUL-free, and contains no .. segment under either separator.

All harnesses are gated behind #[cfg(kani)], so they have zero impact on cargo build, cargo test, or cargo clippy on the stable toolchain. They run only via cargo kani, locally and in the kani CI job in .github/workflows/formal-checks.yml.

An example

A typical Kani harness in kcore looks like this: 

#[cfg(kani)]
mod kani_proofs {
    use super::*;

    const MAX_INPUT_LEN: usize = 8;

    fn any_ascii_str(buf: &mut [u8; MAX_INPUT_LEN]) -> &str {
        let len: usize = kani::any();
        kani::assume(len <= MAX_INPUT_LEN);
        for slot in buf.iter_mut() {
            let b: u8 = kani::any();
            kani::assume(b < 128);
            *slot = b;
        }
        std::str::from_utf8(&buf[..len]).unwrap()
    }

    #[kani::proof]
    #[kani::unwind(17)]
    fn nix_escape_output_is_always_safe() {
        let mut buf = [0u8; MAX_INPUT_LEN];
        let s = any_ascii_str(&mut buf);
        let escaped = nix_escape(s);
        assert!(is_safely_escaped(&escaped));
    }
}

That harness is short, but it replaces an unbounded number of unit tests for the same security property: every possible ASCII input within the bound is checked.

Why both, not one

They cover different ground:

  • proptest scales to bigger inputs and stateful code (like a real SQLite database) and gives fast feedback. It is the right tool when you cannot afford the symbolic state space of exhaustive checking.
  • Kani gives an actual proof within bounds. For the security boundary functions — Nix escaping, path validation — "we tried 2,000 random inputs" is not the same answer as "no bounded input can break this".

In practice, proptest finds the bug, you fix it, and then you write a Kani harness so the same class of bug cannot come back.

What this means for operators

The user-visible result is fewer of the worst kinds of bug: a controller that generates a broken or unsafe Nix config, a database that ends up with dangling VM rows, a path traversal in disk validation. These are bugs that would not show up in a happy-path integration test and that would be expensive to debug in a real cluster. Pushing them out at PR time is much cheaper than catching them in production, and it is one of the reasons every PR in kcore has to pass make check, cargo test --workspace, cargo kani, and the TLA+ model checks before it can merge.
